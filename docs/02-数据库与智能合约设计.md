# 数据库与智能合约设计

## 1. 数据存储原则

系统采用链上链下结合的方式：

- MySQL 保存完整维修业务数据，便于查询和展示；
- 区块链保存维修记录摘要和关键状态；
- Hash 用于证明链下详情与上链时的详情一致；
- 不在区块链中保存车主手机号、身份证号等隐私信息。

### 2.6 关联约束

业务表使用 InnoDB 外键保证关联数据不会脱节：

- `vehicle.owner_id -> sys_user.id`；
- `repair_record.vehicle_no -> vehicle.vehicle_no`；
- `repair_record.repair_shop_id -> sys_user.id`；
- `abnormal_record.repair_record_id -> repair_record.id`；
- `abnormal_record.vehicle_no -> vehicle.vehicle_no`；
- `admin_operation_log.operator_id -> sys_user.id`。

车辆、用户和维修记录采用删除限制；删除维修记录时级联清理其异常检测记录。已有数据库可执行 `cd backend && npm run migrate:integrity` 完成字段和外键迁移；该命令不会自动删除数据，清理确认过的旧孤儿记录时需显式设置 `CLEANUP_ORPHAN_DATA=true`。

### 2.7 `admin_operation_log` 管理员操作日志表

管理员启用或停用账号、复核异常记录、撤销维修凭证、维护质保规则和重新扫描异常时，系统写入操作日志。日志只追加不覆盖，用于展示后台操作过程和支持责任追溯。

## 3. Hash 计算规则

必须保证创建和验证时使用完全相同的字段顺序、日期格式和空值处理规则。建议只对以下字段计算 Hash：

维修商创建维修记录时可以提交 `warrantyRuleId` 选择活动规则。该字段只用于服务端计算 `warrantyEnd`，不参与维修详情 Hash；这样管理员调整规则不会改变已经生成的维修凭证摘要。

```json
{
  "certificateNo": "CERT20260001",
  "vehicleNo": "CAR20260001",
  "repairItem": "更换刹车片",
  "repairTime": "2026-08-25 10:30:00",
  "mileage": 35000,
  "partsInfo": "前轮刹车片",
  "amount": 680.00,
  "warrantyStart": "2026-08-25",
  "warrantyEnd": "2027-08-25"
}
```

维修商提交 `warrantyRuleId` 后，后端只读取活动规则的 `warranty_days` 计算 `warrantyEnd`，前端传入的质保结束日期不会覆盖服务端计算结果。没有匹配规则的历史兼容请求才使用显式质保日期。建议先将 JSON 字段按固定顺序拼接，再使用 SHA-256 计算，避免不同语言序列化格式不同导致验证失败。

## 4. 智能合约设计

### 4.1 链上数据结构

```solidity
struct RepairProof {
    string certificateNo;
    string vehicleNo;
    bytes32 dataHash;
    uint256 repairTime;
    uint256 warrantyEnd;
    address repairShop;
    bool revoked;
}
```

### 4.2 合约映射

```solidity
mapping(string => RepairProof) private proofs;
```

凭证编号作为查询索引，保证同一凭证不能重复写入。

### 4.3 合约方法

```text
addRepairProof
  参数：凭证编号、车辆编号、Hash、维修时间、质保截止时间
  作用：写入维修凭证摘要

getRepairProof
  参数：凭证编号
  作用：读取链上凭证

verifyRepairProof
  参数：凭证编号、待验证 Hash
  作用：比较 Hash 并返回验证结果

revokeRepairProof
  参数：凭证编号
  作用：将凭证设置为撤销状态，不删除链上记录
```

## 5. 关键约束

- `certificate_no` 必须唯一；
- `vin` 必须唯一；
- 维修里程不能为负数；
- 质保结束日期不能早于开始日期；
- 同一凭证不能重复上链；
- 已撤销凭证验证时必须返回失败；
- 数据库写入成功但上链失败时，记录状态应标记为待上链或失败，不能伪装成已完成。
- 管理员重新扫描异常记录时应避免为同一维修记录和异常类型重复创建信号；重新扫描结果和规则维护操作应写入管理员操作日志。
